# Audit du starter du 2 octobre 2026

Sur la version initiale examinée le 2 octobre, le registre signalait 29 alertes dans les
dépendances verrouillées. Les corrections locales portent sur la CI,
les erreurs de formulaires, la concurrence des tests et les instructions de démarrage.
Les PR 37–40 ont ensuite corrigé ces alertes et ont été fusionnées le 2 octobre après revue
indépendante et CI verte. Le présent rapport conserve les constats initiaux ci-dessous.
La CI finale de `main` à `2761ac31` a réussi :
https://github.com/voidcorp-core/void-starter/actions/runs/37023764549.

Le 5 octobre, les corrections locales de cet audit sont reprises dans une PR dédiée.
La PR hebdomadaire 41 apporte un nouveau lot de dépendances ; ses résultats seront vérifiés
sur sa propre révision. Les verdicts datés ci-dessous ne décrivent pas son état actuel.

## Améliorations prioritaires pour les projets dérivés

### Orientation validée par Folpe

« Le starter propose des choix par défaut cohérents, tout en maximisant l’indépendance entre
ses couches. Le socle commun reste minimal ; les capacités optionnelles et les adaptateurs
de fournisseurs sont isolés et remplaçables. Les applications composent ces couches, sans
imposer leurs fournisseurs au socle. Chaque composition prise en charge doit être vérifiée. »

Vérification : revue d’architecture et tests de composition. Formulation explicitement
approuvée le 2 octobre 2026 pour la section `Hard rules` de `.void/PROJECT-DOCTRINE.md`.
L’écriture de ce fichier a été refusée par `PROTECTED_FILE`, malgré le parcours `void-learn`
et la confirmation humaine. La règle est donc consignée ici ; son installation dans la
doctrine reste à faire après correction de ce conflit du harnais.

Pour les propositions ci-dessous, cela implique de vérifier les dépendances entre couches,
la suppression effective des capacités non sélectionnées et le remplacement des adaptateurs.
L’agnosticisme visé concerne les couches et fournisseurs ; aucun changement de langage ou de
stack de référence n’est déduit de cette règle.

### Priorités

1. **Tester chaque profil généré jusqu'au build et à la CI.** Le projet minimal passe doctor,
   mais copie une CI qui exécute encore `cd packages/db` alors que ce package a été retiré.
   Critère : web minimal, Better Auth, Clerk et mobile génèrent chacun une CI adaptée et verte.
2. **Refuser les capacités annoncées mais non implémentées.** Le mode
   `public_signup_gated_activation` est accepté et documenté comme équivalent à `public_verified`.
   Critère : le manifest refuse ce choix tant que le contrôle d'activation n'existe pas.
3. **Rétablir la compatibilité du doctor historique.** Les reçus v1 restent diagnostiquables
   mais provoquent un échec ; le checkpoint signale aussi le contrôle de provisioning historique.
   Critère : définir et tester le statut des deux contrôles sans masquer les corruptions (DEV-686).
4. **Livrer des versions identifiables du starter.** Enregistrer la révision source dans le reçu,
   publier un changelog et des instructions de migration pour les projets déjà créés.
   Critère : un projet peut répondre « de quelle version est-ce que je dérive, et que dois-je migrer ? ».
5. **Vérifier les variables d'environnement sous Turbo.** Le build ne déclare pas ses variables
   dans son cache et le dev ne déclare pas celles à transmettre. Critère : deux configurations
   publiques différentes ne partagent pas un build, et les variables serveur atteignent le runtime.
6. **Terminer la réparation du harnais dans les clones.** La mise à jour vers 4.0.0 a résolu
   neuf des dix échecs initiaux. Il reste la règle `.void/` de `.gitignore`, qui masque les
   entrées d'installation nécessaires au clonage. Le hook refuse sa modification directe.
   Critère : un clone dispose des instructions et hooks attendus ; les projets générés
   continuent d'exclure le harnais.

historique `void-harness` utilisait déjà ce CLI depuis le dépôt local, mais l'installation du

Le doctor final relève **un échec**, deux contrôles distants non exécutés et deux avis : limites

refusée par le hook `PROTECTED_FILE`, qui considère `.gitignore` comme un asset du harnais.
Aucun contournement n'a été effectué. Le lint et `git diff --check` passent après la mise à jour.

La restriction initiale sur les lockfiles a ensuite été clarifiée : leur régénération via Bun
est autorisée. Les mises à jour npm ont été livrées dans les PR 37–40, séparément du harnais.

## Intégration du 5 octobre 2026

Les corrections locales ont été réparties en commits : régression puis correction des erreurs
Zod, indépendance des jobs CI, concurrence Vitest, documentation et assets du harnais.
Les scripts de hooks, la configuration, la doctrine existante et le manifeste sont désormais
explicitement suivis par Git. Les journaux et checkpoints restent locaux.

La première restauration avec le paquet publié `voidmachine@4.0.0` déclarait 174 fichiers
vérifiés, mais la revue a montré qu'elle remplaçait le hook par une implémentation antérieure.
Le manifeste réécrit ne prouvait pas la reproduction du bundle livré. Cette version réintroduit
un défaut de refus Codex sous PowerShell. Le bootstrap final utilise donc la révision source
publique `03580e2d0609d1d98bc5ef06d80512327b811c60`, construite avec le lockfile gelé.
Une nouvelle restauration conserve les hashes SHA-256 des deux bundles committés et restaure
174 assets. Les quatre packs doivent être indiqués explicitement. La procédure est dans le README.

La revue a également reproduit une fuite de `.claude/settings.json` vers les applications
générées, où les scripts `.void` référencés étaient absents. Un test rouge puis vert couvre
la correction : la factory exclut désormais tout `.claude` à la copie, tout en permettant
aux projets générés d'installer leur propre gouvernance ensuite.

La restriction `PROTECTED_FILE` sur `.gitignore` et la doctrine persiste. Le suivi explicite des
assets existants permet leur livraison sans modifier ces fichiers. L'installation de la règle
approuvée dans la doctrine reste un point distinct ; sa formulation est conservée plus haut.
