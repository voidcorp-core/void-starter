## 2026-07-28: Materialize invite_only as a generated constant plus a database ledger

- **Date:** 2026-07-28
- **Decision:** `auth.access_mode: invite_only` now produces code. The factory writes
  `packages/auth/src/access-mode.ts` with the manifest's mode, and `auth.repository.ts` reads it to
  decide whether Better Auth's user-create hooks consult an invitation ledger. Admission is checked
  in the `before` hook and consumption recorded in the `after` hook, against a new `invitations`
  table keyed by a normalized email under a partial unique index
  (`used_at is null and revoked_at is null`). Only a SHA-256 digest of the invitation token is
  stored. The bootstrap administrator is admitted without an invitation, which is what makes the
  first account possible. `invite_only` requires the Better Auth provider; a manifest selecting it
  on Clerk is rejected.
- **Why:** The mode was accepted by the schema since v1 but consumed by nothing: `accessMode`
  travelled into `CompositionPlan.policies` and stopped there. Two projects differing only by
  `access_mode` generated byte-identical code, so a project declared "invite-only internal tool"
  shipped a public `/sign-up` page and an open `signUpEmail` endpoint. Unlike the equivalent
  durable-jobs gap (ADR 62), this one was not a no-op: the manifest asserted an access restriction
  the runtime did not apply. Enforcing in the user-create hook rather than on the sign-up form
  closes all three creation paths at once -- email sign-up, magic link for an unknown address, and
  a social callback -- because hiding a form is cosmetic.
- **Rejected alternatives:**
  - An `AUTH_ACCESS_MODE` environment variable: an invite-only project could then be reopened from
    a provider dashboard with no code change and no trace. The restriction must cost a redeploy.
  - Better Auth's `organization` plugin and its native invitations: imposes organizations, members
    and a second role hierarchy on a tool that is mono-tenant by construction, for a feature we use
    one tenth of.
  - A domain allowlist (`@company.com`): simpler, but it is not invitation. Every holder of a
    company address lets themselves in, no external contractor can ever be admitted, and there is
    no per-person revocation.
  - Storing the token in clear: a database leak would then hand over redeemable links. The token is
    high-entropy and random, so an unsalted SHA-256 is sufficient and a rainbow table has nothing
    to precompute.
  - Consuming the invitation in the `before` hook: any account creation that then failed would burn
    the invitation and lock a legitimate invitee out with no recourse.
  - Pruning `invitations` from the schema on a public project: the published Drizzle migrations
    would desynchronize from the schema. `job_executions` set the precedent -- tables stay, only
    application surfaces are pruned.
  - Distinguishing refusal reasons to the visitor: turns the sign-up endpoint into an oracle for
    who works at the company. All refusals share one message; the reason goes to the structured log.
- **Acceptance evidence:** Helper tests cover normalization, digesting, expiry and the full state
  machine including precedence (`used` over `revoked` over `expired`) and the inclusive expiry
  boundary. Service tests cover bootstrap admission, ledger admission, the four refusal paths, the
  uniform refusal message, consumption, and re-invitation after revocation. Composition tests pin
  the generated constant for both modes, the pruning of the admin surfaces on a public project and
  their retention on an invite-only one, and the retention of the schema in both. Schema tests pin
  the Clerk rejection. Generating two projects that differ only by `access_mode` now produces three
  differing paths (`access-mode.ts`, the manifest and the receipt) plus the invitation admin
  surfaces, where it previously produced none. The live canary remains the final gate.
- **When to revisit:** Materialize `public_signup_gated_activation` the same way, which is still
  declared and still inert. Revisit the ledger shape when a project needs more than one pending
  invitation per address, and revisit the Better Auth prerequisite if a Clerk allowlist adapter is
  ever adopted.
